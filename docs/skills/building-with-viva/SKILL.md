# Building with Viva

Viva is a Go-first, GPU-native desktop framework. It draws its own UI: there is no WebView, HTML, CSS or JavaScript, and nothing is redrawn while the app is idle. Most mistakes come from writing it like a web or retained-mode toolkit. Read this before writing code, and read the guides it points to before guessing an API.

## 1. Decide whose code it is

Before building, sort each need into one of two kinds.

- **Application behavior**: your protocols, storage, workflows, product screens. It stays in your app.
- **A reusable desktop capability**: windows, input, text and IME, focus, layout, components, rendering, accessibility, lifecycle, headless control. If a second Viva app would copy the same helper or wiring, it belongs in Viva, not in your app. Stop and design the smallest self-contained API for it instead of working around the gap with platform calls, synthetic input or hand-written hit testing.

If you are in a checkout of Viva itself, its `AGENTS.md` is the authority and overrides this file.

## 2. Rules that review rejects

- No reflection, `map[string]any` or dynamic property bags in layout, input, scene or render paths.
- No goroutines, timers or polling loops that run while the app is idle. Animation is a scheduled, temporary reason to draw, never a heartbeat. An idle window draws nothing.
- Declaring components and layout must not allocate per paint. State that is expensive to compute (shaped text, line breaks) is cached by whoever owns it and invalidated explicitly.
- Never number hit targets by hand. Identities are names in a `gfx.Tree`; a page (`ui.C`) makes them for its elements.
- Do not add a dependency to the code that ships in the app without measuring its stripped binary size, startup and idle memory.
- Do not claim "zero allocation", "fast" or "light" without a reproducible measurement.

## 3. How a screen is written

The painting function is the UI. It runs again on every redraw, declares what is on screen with value types, and keeps no layout cache. The smallest complete program is [`hello/main.go`](https://github.com/vivaui/viva/blob/main/examples/guides/hello/main.go); the others in [`examples/guides`](https://github.com/vivaui/viva/tree/main/examples/guides) show one concept each (layout, input, text field, overlays, windows, theming, drawing, background).

- A page imports `github.com/vivaui/viva/ui` alone: colors, geometry and the theme are re-exported there (`ui.RGB`, `ui.Rect`, `ui.Theme`, `ui.LightTheme()`). `gfx` is the layer below (Canvas, paths, input events, keys, identities); reach for it only to draw or handle input yourself.
- Write an application page as `func (m *model) page(c ui.C)` and open it with `ui.Run(config, m.page)` or `ui.NewPage(ui.PageConfig{View: m.page}).Config(base)`. Every element is a function of `ui` taking `c` first, and controls write into your values: `ui.Checkbox(c, &m.done, "Done")`, `ui.Choice(c, &m.tab, tabs, nil)`, `ui.TextField(c, &m.name, "Name", "")`, `ui.Modal(c, &m.open, "Title", body, footer)`, `ui.Popover(c, anchor, &m.menu, body)`. A list whose rows hold a `Button` declares each row with `c.Key(item.Name)` or `c.KeyInt(item.ID)`: `ui.Row(c.KeyInt(h.ID)).Children(...)`. A long list is `ui.List(c, &m.list, n, func(row ui.ListRow) { ... })`, which declares only the rows on screen and chooses, moves, submits (`Submitted()`), types ahead (`ListState.Label`) and, with `ListState.Selection`, chooses several, with `ScrollTo`/`ScrollIntoView`/`Visible` to scroll and `box.ClickModifiers()` for any click's modifier keys; `ListState.Header` pins section headings, `Reorder` lets rows be dragged, `RowWidth` scrolls wide rows sideways (`box.ScrollWith(&list)` for a header above); a part that rarely changes is `ui.Memo(c, *row, fn)`, which copies it while that value compares equal. Work that belongs to the page is a `ui.NewEffect[Result, Key](run)` declared with `ui.Effect(c, state, key)` and read once with `state.Take()`: a new key cancels and restarts, a paint that stops declaring it or a closing window cancels it. An element's own small state is `ui.State[T](c, "open")`, found by its name in its container. `ui.TextArea(c, &m.notes, label, "")` is several rows. A control of your own (terminal, editor, canvas) is `ui.Control(c, label, &m.handlers).Draw(m.draw)`, its `ui.Handlers` taking keys, pointer, wheel and (RoleTerminal/RoleTextField) typing through `Text`; it needs no identities or window-level dispatch. `ui.TextField(...).AutoFocus()` focuses a field as it appears and `.Submitted()` reports Enter in it; `.Secure()` makes it a password field. `.Tooltip("Delete")` is a control's tip. `ui.Menu(c, anchor, &m.menu, func(menu *ui.MenuItems) { if menu.Item("Rename").Clicked() { ... } })` is a dropdown menu of actions (typing a letter goes to its item; `menu.Sub(label, body)` is a submenu); `ui.Combobox(c, &m.zone, zones, Zone.String, "Time zone")` is a Select the user filters by typing (`.Clearable()`, `.Empty(text)`, `.Creatable("")` with `.Created()`); toasts are a `ui.Toaster` in the model, `m.toaster.Show(title, description, ui.ToastSuccess)`, painted by `ui.Toasts(c, &m.toaster)` declared once; `ShowAction(..., "Undo")` and `Acted()` give one a button, `ui.ToastLoading` stays until `Done(id, ...)`, `Toaster.Position` picks the corner. `ui.Button(c, "New").Icon(plus)` is a button with an icon. `ui.ContextMenu(c, target, func(menu *ui.MenuItems) { ... })` is a right-click menu (items take `.Icon`, `.Keys`, `.Checked`, `.Chosen`). `ui.TextField(...).Icon(search).Action(cross, "Clear")` is a search field, `.ActionClicked()` its button. `ui.Drawer(c, &m.open, title, ui.DrawerSpec{...}, body, footer)` is a side panel (`Swipe: true` adds a handle that dragging toward the edge closes it by). `ui.Tree(c, &m.tree, n, label, content)` is a virtualized tree whose `TreeState.Node` describes each visible row (typeahead by name; `CanDrop` plus `Dropped()` for drag and drop, the move done in `c.After`); `Toggled()` and `Chosen()` report what the user did. A shortcut is declared where it acts: `if ui.Shortcut(c, ui.Primary, "s") { m.save() }` for the page, `box.Shortcut(0, "delete")` while the focus is in that element (the innermost wins); plain keys stay with a field being typed in. A settings struct gets its form from tags: `form:"Label"` on its fields and `//go:generate go tool viva form` write `func (v *T) Form(c ui.C) ui.Box` (see `viva help form`). [`page/main.go`](https://github.com/vivaui/viva/blob/main/examples/guides/page/main.go) is a complete page.
- A custom layout is `ui.CustomLayout(c, &m.layout).Children(...)`: implement `ui.Layout`'s `MeasureWidth`, `PlaceWidth`, `MeasureHeight` and `PlaceHeight`; the page keeps identity, focus and hits, and the layout owns its children's sizes and positions. PlaceHeight may move a child after heights are measured: the page moves its subtree and re-places its popups. Wrap it in `Scroll`, `List` or `Tree` for scrolling; it is not declared in a `Memo`. `c.Bounds()` and `c.Canvas()` are the page rectangle and canvas for measuring and interaction state.
- Put a strip of controls in one Tab stop with `ui.Row(c).FocusGroup(ui.FocusHorizontal)`; the arrows move between them. `.FocusOrder` gives a custom grid row/column order instead of declaration order.
- Handle a click where the control is declared: `ui.Button(c, label).Clicked()` is true for the one paint that delivers the click, and only then may state change. A handler that changes the list being declared, or may block, goes in `c.After(func() { ... })`. `Choice`, `Tabs` and `Select` write as they are declared: disable them with an `if`, not a `Disabled` after them.
- Use a `ui.Frame` only when writing a component that paints through it (`ui.View.Draw`): a component with its own identities, or a test that addresses a control by path. Application pages do not reach the Frame; inside a page, `ui.ID(c)` names a custom control by its place (or the Key or `c.Part("word")` before it). In a Frame of your own, declare identities once: `tree = gfx.Tree{}`, a `tree.Feature("name")` per area, `tree.ID(feature, "control")` per control, never numbered by hand. Focus, hover and press are tracked by ID, and `Canvas.Focused`, `Canvas.FocusVisible` and `Canvas.Hovered` report them back.
- Layout is `ui` either way. Components are source-distributed, typed Go, one file per component; read the file rather than looking for a hidden style engine.
- Make it look finished by taking, not inventing: colors from the theme (`theme.Card`, `theme.MutedForeground`, `theme.Border`), radii from `theme.Metrics`, lengths in multiples of 4, and state from looks (`Hover`, `Pressed`, `Focus`, `Transition`) rather than hand-read canvas state. [`examples/recipes`](https://github.com/vivaui/viva/tree/main/examples/recipes) holds nine finished components written that way (settings row, list row with a hover pencil, avatar with presence dot, badge, stat card, gradient hero, toolbar icon button, empty state, dimmable section), each tested in both themes: copy the nearest one and change it before composing from scratch. [`recipes.md`](recipes.md) says which to start from and what to avoid.
- Prefer a few intention-revealing parameters. When same-typed positional arguments pile up, use a small struct or chainable options.

## 4. Verify without opening a window

Do not open a real window unless the user agrees; it interrupts them and depends on which display it lands on. Use these in order of cost.

1. **`app.Driver`** in a Go test: runs your real painter, router and focus rules from explicit calls (`Click`, `Key`, `Type`, `Scroll`, `Advance`) and returns a `Snapshot` of labels, hit regions and focus; `app.NewDriver(ui.NewPage(ui.PageConfig{View: m.page}).Config(base), nil)` drives a page, whose controls a test finds by their name (`Hit.Label`). See [`hello/main_test.go`](https://github.com/vivaui/viva/blob/main/examples/guides/hello/main_test.go). Test behavior a user depends on, not pixel offsets or exact primitive counts.
2. **Headless build and line protocol**: import `github.com/vivaui/viva/headless/auto` from a file guarded by `//go:build vivahead`, so release builds never contain it. Build with `-tags vivahead` and start the program with `VIVA_HEADLESS=1` and a throwaway `HOME`: `RunCanvas` then reads one command per line from stdin instead of opening a window (`click "Label"`, `type`, `key`, `waitfor`, `shot`, `texts`, `layout` ...). Each reply ends in one `ok` or `error` line. The complete command list is the comment above `Serve` in [`headless/control.go`](https://github.com/vivaui/viva/blob/main/headless/control.go); do not copy it elsewhere, it would go stale.
3. **`layout`** lists text that is clipped, spills out of its control or lies over other text. It is faster to read than a screenshot; use `shot` when the look itself matters.
   **`tree`** lists every control with its role, identity, accessible name, value and state (focused, disabled, checked, covered ...); read it first to learn what the frame can do. A control with no name is reached by identity or role: `click id:home/auto`, `click checkbox:`, `click "button:Save"`. **`expect`** turns a look into a check that fails with what the frame has instead: `expect text "Connected" within 5000`, `expect state id:home/auto checked`, `expect layout clean`, `expect named`. Prefer a script that ends in `expect` lines to one you read by eye, and put `expect` lines in the Go test for anything a user depends on (`Session.Expect` takes the same words). When a step fails: not found, run `tree`; text cut off, `layout`; focus wrong, `focus`; a press does nothing, look for `covered` in `tree`.
4. **Real windows** on each target platform for anything the above cannot see: IME, focus loss, window-manager close, physical keyboard, high-DPI. Say plainly what you did not test.

Before finishing, run `gofmt`, `go vet ./...`, `viva vet` (or `go tool viva vet`) and `go test ./... -count=1`. `viva vet` reports the page mistakes that compile: a constant-labeled `Button` in a loop whose rows have no `c.Key`/`c.KeyInt`, a `ui.C`, `Box` or `Frame` kept in a struct/global or given to a goroutine, and a `ui.Memo` whose value misses a field its function reads; each finding says what to write instead. Run tests with `ui.MemoCheck(true)` (or `PageConfig.MemoCheck`) when a page uses `Memo`: it panics where the value misses something the part reads. For painting or input paths, report allocations per paint and steady-state time with `go test -bench`; for a change that affects linking, report the stripped binary size before and after.
